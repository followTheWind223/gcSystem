# 若依统一认证与普通用户权限

2026-10-23 用户确认变更；契约 3.0.0，数据库 V007。替代此前独立会员登录设计。

用户端直接请求若依原生 Controller：`GET /captchaImage`、`POST /register`、`POST /login`、`GET /getInfo`、`POST /logout`。浏览器通过 `/api/auth` 代理前缀调用，代理去掉此前缀；后台仍使用 `/admin-api`。商城业务 `/api/mall` 前缀保持原样。

## 注册和登录

验证码响应为顶层 `captchaEnabled`、`uuid`、`img`（图片 Base64）。验证码开启时，登录和注册提交 `uuid`、`code`；验证码一次性消费，失败后重新获取。使用若依的验证码、密码校验、失败计数、令牌服务和 Redis 会话，不再签发商城独立 JWT。

```json
{"username":"shop_player","password":"Example123!","nickname":"商城玩家","email":"player@example.com","uuid":"example-captcha","code":"7"}
```

以上为 `POST /register` 请求：用户名 2–20 字符；若依密码允许 5–64 字符，商城新密码表单要求 8–64 位且包含字母和数字；昵称可选、填写时 2–30 字符；邮箱为联系信息，最多 254 字符。服务端忽略客户端传入的角色、部门和用户 ID，固定分配 `common`（普通用户）。注册与角色写入同一事务，用户名数据库唯一索引防止并发重复。

注册成功响应：

```json
{"code":200,"msg":"操作成功"}
```

`POST /login` 只提交 `username/password/uuid/code`。成功响应的 token 在顶层：

```json
{"code":200,"msg":"操作成功","token":"example-ruoyi-token"}
```

若依业务错误可能使用 HTTP 200、`code=500`，前端必须检查业务 code，例如：

```json
{"code":500,"msg":"用户不存在或密码错误。"}
```

`GET /getInfo` 使用 `Authorization: Bearer <token>`，返回顶层 `user`、`roles`、`permissions` 等既有若依字段。普通用户 `roles=["common"]`、`permissions=[]`；密码不返回。商城登录后读取 `/api/mall/me` 获取业务档案与会员 ID。管理员也可登录商城，自己的商城档案独立关联，不继承其他会员订单。

## 普通角色只使用商城

V007 将原 `common` 普通角色更名为“普通用户”，移除其全部菜单和部门范围关联，不删除账号。权限计算也排除该角色的后台权限；后台安全链要求实际管理权限，仍叠加每个接口的权限注解。普通用户访问 `/getRouters`、`/system/**`、`/monitor/**`、`/tool/**`、`/mall/**` 被拒绝，后台前端登录时提示使用商城用户端。

有其他管理角色的账号按其他角色权限授权；超级管理员保留后台权限。`/getInfo` 是两端共用的个人身份接口，普通用户可以调用，不代表可进入后台。

## 会话与商城业务身份

若依令牌以 `login_tokens:` Redis 会话为准，默认 30 分钟并按若依逻辑续期。商城只保存在 Pinia 内存，不与后台共享 Cookie 或持久化存储。退出使用原生 `/logout`；账号禁用、删除、密码变化使旧令牌在下一次访问时失效。服务端会话保存凭证指纹，旧版未带指纹的会话需重新登录。

`mall_member.sys_user_id` 是唯一外键；`member_id` 保留作为交易归属，不将 sys_user 数字 ID 直接当会员 ID。新用户首次访问受保护商城接口时建立档案；使用用户行锁和当前读避免并发重复建档。购物车、订单、报价和评价继续使用当前关联会员的归属校验。

资料、改密和头像接口仍为 `/api/mall/me`、`/api/mall/me/password`、`/api/mall/me/avatar`；昵称、联系方式、密码写回 sys_user，头像沿用商城受控媒体。后台会员停用表示停止该档案的商城访问，系统账号停用则使统一会话失效。

旧 `/api/mall/captcha`、`/email-codes`、`/members`、`/sessions`、`/sessions/current`、`/password-resets` 已移除。邮箱验证与邮箱找回不启用，旧 `GAMESHOP_EMAIL_VERIFICATION_ENABLED` 不控制若依注册；忘记密码由管理员重置。

## 数据迁移

先备份，依次执行 V001–V006，再执行 V007。V007 不是可直接重复执行的 DDL，应依据 mall_schema_history 跳过已完成版本。发现商城与系统同名账号、重复系统用户名或缺少 common 角色会在结构修改前拒绝迁移，禁止自动合并身份。

历史商城账号写入 sys_user，保留原 BCrypt 密码、昵称、联系信息和状态，分配 common，随后建立关联并清空 mall_member.password_hash；不改变会员主键或订单、购物车、评价引用。sys_user 增加用户名唯一索引、邮箱扩至 254 字符、手机号扩至 20 字符。mall_member 邮箱允许为空且不再唯一；密码字段保留为空以兼容历史结构，不再参与认证。
